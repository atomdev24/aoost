# Decisions

One line each: the decision, and why. Newest at the bottom.

- Everything for the CMS lives in `cms/` (its own `package.json`); content lives in `content/` at the repo root. Why: keeps the GitHub Pages site files untouched until cut-over.
- `wrangler.toml` lives in `cms/`; `npm run dev` symlinks the root `.dev.vars` into `cms/` (both gitignored). Why: wrangler only reads `.dev.vars` beside its config, and Alex's file is at the root.
- The admin SPA is a plain Vite build served at `/admin/` from Worker static assets (no Cloudflare Vite plugin). Why: fewer moving parts; `wrangler dev` serves the built files.
- `assets/fonts/FacileSans-Regular.otf` is committed so the deploy Action can build with it. Its note says "Freeware, Non-Commercial"; see `BLOCKERS.md` for the licence check.
- Content files: `content/site.json` (settings, theme, nav, globals, templates, redirects, page order), `content/collections.json`, and one `content/pages/<id>.json` per page. Why: readable git diffs and per-page history.
- Diary entries and playlists are collections (`content/collections.json`), rendered by the Diary list and Playlist card components, not one page each. Why: the site is a diary feed; it makes quick-edit "add an entry/playlist" a one-form action and keeps page nesting one level deep.
- "Show in navigation" is a `showInNav` flag on the page. A page-link nav item whose page has visible sub-pages renders as an automatic dropdown (matches the mockup's caret behaviour).
- Colours in content can be `token:<name>`; they render as CSS variables, so editing a theme token restyles the whole site without touching pages.
- Canvas sections store layer boxes in design px (390 mobile, 1440 desktop) and render as percentages of an aspect-locked artboard, so they scale with no layout JS.
- Seed images reference the existing `/art/*` files (copied into the build output, originals untouched). Socials are generic instagram.com / spotify.com links until Alex sets his profiles in Site settings.
- The Rodeo page links to the current site's game; migrating the game itself is out of this run (SPEC §10).
- Desktop breakpoint starts at 900px (`DESKTOP_MIN`). Why: below that the pill nav's link row and multi-column grids get cramped; tablets in portrait get the mobile layout until a tablet breakpoint exists.
- A canvas layer with no desktop position is derived by scaling the mobile artboard uniformly to fit a band at most 720px tall, centred in 1440px. Why: literal width scaling (×3.7) makes sections absurdly tall.
- Text sizes are emitted as `calc(var(--cs, 1px) * N)`: inside a canvas `--cs` is one design px, so type scales with the artboard; elsewhere it is 1px.
- Components keep their CSS in a `*.styles.ts` string, not a `.css` file. Why: the same component code runs under Vite (editor), tsx (build) and the Worker (draft preview), and a TS string is the one format all three import without loader config.
- Pages are written as `work.html` / `work/digital.html` so Cloudflare serves clean URLs (`/work`). All CSS is inlined per page (only the components that page uses) and there is one deferred script (`/assets/site.js`, ~8 KB).
- Text content supports only `**bold**`, `*italic*`, `[links](url)` and line breaks, rendered as React nodes. Why: no raw HTML in text means nothing to sanitise; the Code block is the place for custom HTML.
- A page link with sub-pages uses a split control in the pill: the label navigates, the caret button opens the menu (works for hover, tap and keyboard).
- The draft lives in a SQLite-backed Durable Object (free plan) as the same files as `content/`; changes travel as page-granular ops (last write wins per page). Why: publishing becomes "commit these files", and live sync stays simple.
- The editor uses Puck's own layout (plugin rail, canvas zoom, fields) re-themed dark, with our top bar and panels plugged in, instead of a hand-built layout. Why: Puck's drag and overlay maths depend on its own canvas zoom.
- The editor keeps its own undo stack at site level (it must also hold page, nav, theme and Claude edits); Puck is a view of the current page.
- Free canvas: Puck keeps selection, but dragging/resizing layers is our own pointer controller inside the preview iframe (Puck's list drag is switched off for canvas layers). Moves commit to the editor store as one undo step. Resize ignores a layer's rotation (handles act on the unrotated box).
- Puck selects one item, so multi-select exists only on a canvas (Shift-click). Align works on one layer (to the artboard) or several (to each other); distribute needs three or more.
- Grid "drop zones" are shown as column guides in the editor; cells auto-flow and each cell can span columns/rows. "Split into 1/2/3/4/6" sets the column count for the active breakpoint.
- Overlays live on the page (`page.overlays`), outside Puck's tree: they are added from the Layers panel, drawn on the canvas, and edited in their own right-hand panel. An overlay attached to a section sits centred on that section's top or bottom edge (straddling it) and can be nudged; attached to the screen it is `position: fixed`.
- Hide is per breakpoint (it writes `hidden` at the active breakpoint); lock and rename are shared.
- Publish commits to the branch in `PUBLISH_BRANCH` (set to `cms-v1` for this run, never `main`). Change that one var at cut-over. The ref update is not forced, so a publish can never overwrite someone else's commit.
- After a publish the draft store keeps a snapshot of what it published, so "Unpublished changes" clears right away instead of waiting for the deploy.
- Undo/redo is the editor's own site-level stack (100 steps, edits to the same field within 1.2 s merge into one step). ⌘Z/⇧⌘Z are captured before Puck's own history.
- New pages start as Draft (Alex publishes them from Page settings), even though the mockup's sample data shows Published. Why: a half-built page should not go live with the next Publish.
- Changing a URL keeps every earlier redirect pointing at the newest URL, and a redirect is dropped the moment a live page takes that URL again. Deleting a page redirects its URL (and its sub-pages') to home.
- A page with sub-pages cannot itself be nested (one level deep, SPEC §5); "Place it" only offers top-level parents.
- A mega menu's panel is stored as sections on the nav item and edited on the same canvas as a page (the editor treats it as a page with id `mega:<item id>`). Why: "built with the same editor" for free: same components, layers panel and CSS generator.
- Simple dropdowns use the ARIA menu-button pattern (arrow keys, Home/End, Escape returns focus). Mega panels hold arbitrary content, so they are a disclosure (button with `aria-expanded`), not a `role="menu"`.
- Search runs in the browser over `search.json`, built with the site. No search service.
- Image resizing: the editor makes WebP variants (480/960/1600/2400 px, never upscaled) in the browser at upload and stores them in R2 beside the original; `/media/<key>?w=N` serves the smallest variant that is wide enough, or the original. Why: Cloudflare's image transformations need a paid plan or a zone setting, and the rules say free tiers only. AVIF is not generated (browsers can't encode it); AVIF originals are served as they are. If Images is ever enabled, only `worker/media.ts` changes.
- Media keys are `<year>/<name>-<random>.<ext>` and never reused, so files are cached for a year (`immutable`). Uploaded SVGs are served with a sandbox CSP so they can't run script.
- Lottie and 3D each ship as their own script (`/assets/lottie.js` 172 KB, `/assets/model-viewer.js` 1 MB), loaded only on pages that contain that block. Why: keeps every other page at one ~9 KB script.
- YouTube/Vimeo videos with a poster load the player only when clicked; embeds use `youtube-nocookie.com`. Why: no third-party requests or cookies until a visitor asks for the video, and a better Lighthouse score.
- Custom code is sandboxed by default (`<iframe sandbox="allow-scripts" srcdoc>` without `allow-same-origin`, auto-height via postMessage checked against the frame's window). Inline mode is opt-in with a warning, and its script never runs inside the editor, only in Preview and on the site.
- Facile Sans is wired in as the display face from `assets/fonts/FacileSans-Regular.otf` (served at `/fonts/`, preloaded, `font-display: swap`). Only the Regular weight exists, so the face is declared for weights 400-700 to avoid browser-faked bold on headings. It is an all-caps face, so headings render in capitals. Space Grotesk stays in the stack as the fallback.
- The Google Fonts picker is a short curated list plus free typing (no Google API key needed); fonts load through the normal `fonts.googleapis.com/css2` link with `display=swap`.
- Durable Objects work on the free plan (SQLite-backed class), so the KV + polling fallback was not needed.
- Live sync is last-write-wins per page: a remote change to a page replaces the editor's copy of that page. If Alex is mid-edit on the very same page in the same second, his unsaved keystrokes on that page can be overwritten (his autosave runs 0.7 s after each edit). Remote changes land on his undo stack, so nothing is unrecoverable.
- `/mcp` is a stateless streamable-HTTP MCP server written by hand (JSON-RPC over POST, JSON responses, no sessions or SSE stream). Why: it fits a Worker without extra dependencies and every tool is a single request/response.
- MCP tools are pure functions of the draft site; the Worker validates the result and sends the difference to the draft store. An invalid result changes nothing and the error text goes back to Claude. `add_node` was added beyond the SPEC list because adding a component to an existing section is the most common request.
- `get_preview_screenshot` is captured by the open editor (the draft preview drawn through SVG foreignObject onto a canvas), not Cloudflare Browser Rendering. Why: Browser Rendering needs enabling on the account and has a small free allowance; the editor route costs nothing. It needs the editor open, and third-party embeds appear as labelled boxes.
- `publish` is gated by its tool description and the server instructions ("only when Alex explicitly asks"). It is not technically blocked, by design (SPEC §8).
- Claude.ai's web connector dialog cannot send a bearer header, so today the connector works with Claude Code and other header-capable MCP clients; the web dialog is revisited with Cloudflare Access.
- Below 900px the editor is quick edit: text, image swaps (upload from the phone or pick from the library), button labels, diary entries, playlists, undo, preview and publish. Sections, layout, nav and theme are desktop-only.
- Performance (Lighthouse mobile ≥ 90): third-party frames get their address only when scrolled near, the Lottie and 3D scripts load only when their block is near the viewport, the Google Fonts stylesheet loads without blocking first paint, and the repo's own `/art` images get WebP copies at 480/960/1600px at build time (via `sharp`, a build-only dependency). Result on the deployed preview: `/sample` 99, `/` 100, `/diary` 100.
- The preview is deployed as the Worker `aoost-cms` at `https://aoost-cms.aoost-cms.workers.dev` (the account's workers.dev subdomain was created by the first deploy). `EDITOR_PASSWORD` and `GITHUB_TOKEN` were copied from `.dev.vars` into Worker secrets.
- The README for this project is `cms/README.md`; the root `README.md` belongs to the existing GitHub Pages site and was left alone.

## Homepage port (HOMEPAGE.md)

- The original homepage is rebuilt from nine blocks in `cms/src/components/aoost/` (Hero, Projects, Journals, Tools, PlaylistBand, DrawingWall, Rodeo, Footer, Viewer), each in its own section of `content/pages/home.json`, in the original order. Why: one block per original section, as HOMEPAGE.md decided.
- **Result of the visual check:** the captures of the original and of `/` are pixel-identical at 390 and 1440 (0 pixels differ; `node scripts/compare-home.mjs && node scripts/diff-home.mjs`). No visual differences remain to list. Both captures are taken with reduced motion and with the same clock minute, so moving parts sit still.
- The CSS is lifted from `index.html` by `cms/scripts/port-aoost-css.py` (by line range) and every rule is scoped under `.ao`, the class the page's `<main>` gets. Why: "port, don't redesign", and the styles cannot leak into other pages or the nav. Re-run the script if `index.html` ever changes; never edit the generated `*.styles.ts` by hand.
- The JavaScript is the original's, moved into `cms/src/components/aoost/runtime/*.js` (plain JS, one file per section) and bundled to `/assets/aoost.js`, loaded only on pages that use these blocks. Each file marks the few lines that changed (where data comes from; where overlays are appended).
- Content comes from the blocks' fields, not from Supabase's `site_content` any more. The defaults are a copy of the live content on 15 Nov 2026 (7 projects, 3 playlists, 4 journals incl. the page made in Atom, 4 ticker lines, 6 skills). Why: HOMEPAGE.md asks for fields. Consequence: content changed in the Atom app no longer shows up on the new site; edit it in this editor instead.
- Supabase is still used, with the same project and publishable key as `index.html`, for exactly what is live data: the rodeo leaderboard, the visitor count and "people here now". A test checks the key and URL equal the original's.
- The editor's draft preview and a local dev server only read from Supabase; they never add visits, presence or scores. The workers.dev preview behaves like the real site (it counts visits and saves scores). Why: testing must not pollute the live counter and board.
- The home page hides the site's pill nav (`hideNav` on the page; switch "Site navigation on this page" in Page settings). Why: the original has no nav. Other pages keep theirs.
- The two cutting mats (light: projects, journals, skills; dark: playlists, wall, rodeo, footer) are rebuilt by wrapping neighbouring sections whose blocks ask for the same mat. Each block has a "Cutting-mat background" field. If you reorder so that light and dark blocks alternate, you get several shorter mats; that is expected.
- The "Alex · Cape Town" line with the cactus, and the longhorn skull, belong to the Projects block (they sit inside the light mat in the original); the scorpion belongs to the Footer. HOMEPAGE.md listed all three under the hero, but in `index.html` that is where they are.
- The original hero has no headline or body copy, so the Hero block's text fields are the corner label ("aoost / portfolio"), the clock label and time zone, the reel images and seconds per image, and the ticker lines (each with when it shows: day, late or both), plus switches for the top-score and visitor lines.
- Projects have title, year, medium, link and tags fields. The original shows none of these on the table, so they appear as the caption in the full-screen viewer (and as the image description). Empty fields change nothing.
- Playlists: Spotify's own playlist name replaces the title once Spotify answers (as in the original); the title field is the stand-in until then. "Colour" is the frame colour behind the cover.
- The drawing wall is off by default, as on the live site. Its menus, tools and panels are the original markup, kept as one piece (`wall.markup.ts`); the editable parts are on/off, the heading and the three palettes.
- The Rodeo block's "copy" field is empty by default because the original has no text there. With the leaderboard switched off the board is hidden and a new best is not offered a place on it; the game itself is unchanged.
- The Footer can also show links from the site's socials; off by default because the original footer has none.
- The Viewer block has no fields and takes no room; keep it on the page, since the reel, the projects and the sticky note open in it. Use one of each aoost block per page: the original script finds its elements by id.
- On the editor canvas the blocks show their first paint only (the scripts do not run there): the reel shows its first image, the table shows a tidy grid, the game shows an empty track. Use Preview to see and try the real thing. Why: running the game and Spotify inside the editor would fight with selecting and dragging.
- The CMS's own image lightbox class was renamed from `.lb` to `.lbx`, because the original leaderboard already uses `.lb`.
- Quick edit on a phone lists the aoost blocks but does not edit their fields; use the full editor (900px and wider) or Claude for those.
- The older browser tests were moved off the home page: nav tests use `/about`, `/work` and `/sample`, editor tests use the sample page. New tests: `tests/home.spec.ts` (behaviour and the pixel comparison) and `tests/home-editor.spec.ts` (editing, preview, `/mcp`).

## Editor redesign (EDITOR-REDESIGN.md)

- The stored format is unchanged: the base is still mobile and desktop stores overrides (SPEC §3), so public pages render byte for byte as before. The editor presents desktop as the reference and mobile differences as "mobile overrides" (blue dots, "Reset to desktop"), as the brief asks. An edit made while Mobile is active writes the base and first keeps desktop's current value as a desktop override (`setOnly` in `cms/src/responsive/resolve.ts`), so desktop does not change. Why: the brief wants per-frame edits "following the existing responsive model" and a schema change would alter stored content.
- Limitation of that rule: a property with no value anywhere (for example an unset padding) that is set on Mobile also shows on Desktop, because the stored format cannot say "unset on desktop". Desktop can still override it.
- Hiding a block on Mobile now leaves it visible on Desktop (before, hiding on mobile also hid desktop unless desktop had its own setting). Why: same "this breakpoint only" rule.
- Browser tests start the local Worker with `--var AUTH_MODE:password` (production stays on Cloudflare Access) and take `E2E_PORT` when 8787 is busy. Why: the tests sign in with the editor password; production settings are not touched.
- Before this work, 14 browser tests already failed on `main` because every page except the homepage is a draft (commit 6af6862), so `/about`, `/sample` and friends are 404 on the built site, plus the Cape Town clock test. They are unrelated to the editor and were left as they are.
